# ТЗ: telegram_bewitched_plugin

Доработка официального Telegram-канала Claude Code (`anthropics/claude-plugins-official`, `external_plugins/telegram`, v0.0.7).

| | |
|---|---|
| Репозиторий | https://github.com/deniskelin/telegram_bewitched_plugin |
| Базовая ветка разработки | `develop` |
| Версия документа | 0.2, 2026-10-28 |
| Целевой Bot API | 10.2 (обязательно), 10.3 (опционально, если доступно) |

### Принятые решения

| # | Вопрос | Решение |
|---|---|---|
| 1 | Стримить сам ответ, а не только ход работы | Пока нет. Вынесено в feature requests (§13, FR-1). |
| 2 | Топик на проект или на сессию | **На проект** (`TOPIC_MODE=project` по умолчанию). |
| 3 | Синтез речи по умолчанию | **Silero TTS** (локально). Piper — лёгкий фолбэк. |
| 4 | Где держать топики | **В отдельной форум-супергруппе.** Группа подключается из лички с ботом (§5.2). Топики в личке — альтернативный режим. |
| 5 | Как запускать демон | Автозапуск из первой сессии, без автоостановки; ручной запуск `bewitched daemon start` (для `@reboot` в cron). systemd не используется: сервер работает в контейнере без systemd (§7.2). |
| 6 | Кнопка «Стоп» с реальным прерыванием хода | **Да.** Через tmux: `Escape` в панель сессии (§2.3.6). |

## 0. Контекст и ограничения платформы

Это требования, которые определяют архитектуру всех фич. Их нельзя «обойти» кодом плагина.

### 0.1. Что есть сейчас (v0.0.7)

- Один файл `server.ts` (~1050 строк): MCP-сервер по stdio, внутри тот же процесс делает long polling `getUpdates` через grammY.
- Инструменты: `reply`, `react`, `download_attachment`, `edit_message`.
- Поддерживаются: доступ по pairing/allowlist (`access.json`), группы с упоминанием, relay разрешений кнопками (`claude/channel/permission`), PID-файл против зависших поллеров.
- Состояние: `~/.claude/channels/telegram/` (`.env`, `access.json`, `inbox/`, `approved/`, `bot.pid`).
- Библиотека: grammY 1.41.1, `@grammyjs/types` 3.25.0. **Типов для методов Bot API 10.x (rich messages, ephemeral, `can_stop`) в этой версии нет.** Новые методы нужно вызывать через `bot.api.raw` / собственную типизированную обёртку либо обновить grammY, если вышла версия с поддержкой 10.x.

### 0.2. Контракт канала Claude Code

- Канал → Claude: только уведомление `notifications/claude/channel` с `content` (строка) и `meta` (`Record<string,string>`). **Ключи `meta` — только буквы, цифры и `_`.** Ключи с дефисом молча отбрасываются.
- Канал может присылать события **без входящего сообщения пользователя** (например, вебхук), сессия на них реагирует.
- Claude → канал: только `notifications/claude/channel/permission_request`. **Текст ответа модели и его стриминг через протокол канала не передаются.** Текст попадает в Telegram, только когда модель вызывает инструмент (`reply` и т. п.).
- Текст модели по мере генерации можно получить только через **хук `MessageDisplay`**. Он отдаёт пачки готовых строк (`delta`) с флагом `final`, а не токены. Хук нельзя блокировать дольше короткого таймаута (по умолчанию 10 с), Claude Code ждёт его завершения на каждой пачке.
- Хуки прогресса: `PreToolUse` (`tool_name`, `tool_input`), `PostToolUse`, `PostToolUseFailure`, `Stop` (`last_assistant_message`), `SessionStart`, `SessionEnd`, `UserPromptSubmit`. Общие поля: `session_id`, `transcript_path`, `cwd`.

### 0.3. Загрузка форка

Во время research preview `--channels` принимает только плагины из allowlist (`claude-plugins-official`). Форк запускается так:

```
claude --dangerously-load-development-channels plugin:telegram-bewitched@<marketplace>
```

- При запуске показывается полноэкранное подтверждение, его нужно принять интерактивно (это работает в tmux).
- С `-p` и в Agent SDK флаг игнорируется: канал не регистрируется.
- Репозиторий должен содержать `.claude-plugin/marketplace.json`, чтобы его можно было добавить как marketplace (`/plugin marketplace add deniskelin/telegram_bewitched_plugin`).

### 0.4. Ограничения Telegram, важные для ТЗ

| Возможность | Ограничение |
|---|---|
| `sendMessageDraft` / `sendRichMessageDraft` | **Только личные чаты.** Черновик живёт ~30 с, затем исчезает. Итог обязательно фиксируется `sendMessage` / `sendRichMessage`. Пустой `text` показывает плашку «Thinking…» (10.0+). |
| Rich-сообщения | 10.1+. До 32768 символов, 500 блоков, 16 уровней вложенности, 50 медиа. |
| Блок «размышления» | `InputRichBlockThinking` / `<tg-thinking>` (10.2), **только в `sendRichMessageDraft`**, в итоговое сообщение не попадает. |
| Кнопка «Стоп» в черновике | `can_stop`, `keep_on_stop`, апдейт `stopped_message_generation` (10.3). |
| Топики в личке с ботом | 9.3/9.4. Включаются в @BotFather. Есть `createForumTopic`, `editForumTopic`, `deleteForumTopic`, `unpinAllForumTopicMessages`. **Метода «список топиков» нет**, `closeForumTopic`/`reopenForumTopic` в личке не поддерживаются. |
| Кнопки | `callback_data` до 64 байт. `style` (`danger`/`success`/`primary`, 9.4), `disabled` (10.3). |
| Голосовые | `sendVoice`: OGG/Opus, MP3 или M4A, до 50 МБ. |
| Опрос | Один потребитель `getUpdates` на токен, иначе 409 Conflict. |

## 1. Архитектура (целевая)

```
                    ┌──────────────────────────────┐
 Telegram  ◄──────► │  bewitched-daemon (1 шт.)    │
 Bot API            │  • единственный getUpdates   │
                    │  • маршрутизация по топикам  │
                    │  • очередь/лимиты отправки   │
                    │  • SQLite: история, реестр   │
                    │  • STT / TTS провайдеры      │
                    │  • HTTP 127.0.0.1 для хуков  │
                    └──────┬───────────────┬───────┘
              unix socket  │               │  unix socket
                    ┌──────┴─────┐   ┌─────┴──────┐
                    │ MCP-сервер │   │ MCP-сервер │   (тонкий клиент,
                    │ сессии A   │   │ сессии B   │    по одному на сессию)
                    └──────┬─────┘   └─────┬──────┘
                       stdio│              │stdio
                    Claude Code A     Claude Code B
                       ▲ хуки MessageDisplay / PreToolUse / Stop → HTTP демона
```

- **Демон** — отдельный долгоживущий процесс (Bun). Он один владеет токеном для опроса.
- **MCP-сервер** (`server.ts`) становится тонким клиентом: регистрирует сессию у демона, получает адресованные ей входящие и передаёт в Claude, проксирует инструменты.
- **Хуки** Claude Code (поставляются с плагином в `hooks/hooks.json`) шлют прогресс и текст в демон по HTTP на `127.0.0.1` с токеном.
- Транспорт демон ↔ клиент: unix-сокет `STATE_DIR/daemon.sock` (права 0600), протокол JSON-lines. Опрос файлового inbox не используется.

Новый каталог состояния: `~/.claude/channels/telegram-bewitched/`. При первом запуске выполняется миграция из `~/.claude/channels/telegram/` (`.env`, `access.json`) с подтверждением. Официальный плагин и форк не должны одновременно опрашивать один токен (см. §7).

## 2. Фича 1. Постепенный вывод текста (стриминг)

### 2.1. Цель

Пока Claude работает над ответом, пользователь в Telegram видит живой черновик. Сначала «Thinking…», затем ход работы и текст ответа по мере появления. В конце черновик заменяется итоговым сообщением.

### 2.2. Источники данных

| Источник | Что даёт | Использование |
|---|---|---|
| Хук `UserPromptSubmit` / входящее из канала | Начало хода, `chat_id`, топик | Открыть «стрим-сессию», показать «Thinking…» |
| Хук `PreToolUse` / `PostToolUse` | Имя инструмента, краткие аргументы | Строки прогресса: «🔧 Bash: npm test», «📖 Читаю server.ts» |
| Хук `MessageDisplay` | Пачки строк текста модели (`delta`, `final`) | Текст в блоке «размышления» или в теле черновика |
| Инструмент `reply` | Итоговый ответ | Фиксация: `sendRichMessage` / `sendMessage`, закрытие стрима |
| Хук `Stop` | Конец хода | Страховка: закрыть висящий черновик |

> Текст, который модель пишет в транскрипт, и текст, который она отправляет через `reply`, — разные вещи. Поэтому стримится **ход работы** (размышления, действия), а финальный ответ приходит через `reply`. Стриминг самого ответа — feature request FR-1 (§13).

> **Где работает нативный стриминг.** Draft-методы Telegram работают только в личных чатах. Основное место работы — топики форум-супергруппы (решение 4), поэтому **основной режим там — «живое» служебное сообщение** через `editMessageText` (п. 7). Нативные черновики (`sendRichMessageDraft`) используются, когда диалог идёт в личке с ботом. Оба режима реализуются одним модулем `stream/` с двумя «рендерерами».

### 2.3. Требования

1. **Привязка хода к чату.** Демон хранит для каждой сессии «активный чат»: последний входящий `chat_id` + `message_thread_id`. Хуки передают `session_id`, демон по нему находит чат. Если активного чата нет (ход начат из терминала), стрим не запускается.
2. **Draft API Bot API 10.2:**
   - основной метод `sendRichMessageDraft`: блок `InputRichBlockThinking` (размышления/прогресс) + `InputRichBlockParagraph` (текст);
   - фолбэк `sendMessageDraft` (plain text, `entities`), если rich недоступен или вернул ошибку;
   - один `draft_id` на ход: ненулевое целое, уникальное в рамках чата.
3. **Темп обновлений.** Не чаще 1 вызова в ~700 мс на чат (настраивается `STREAM_MIN_INTERVAL_MS`). Пачки между вызовами склеиваются. Если изменений нет дольше 20 с, повторно отправляется текущее состояние (keep-alive против 30-секундного таймаута черновика).
4. **Лимиты.** Черновик обрезается до лимита (4096 символов для plain, 32768 для rich). Показывается хвост текста с пометкой «…» сверху.
5. **Фиксация.** Вызов `reply` в чат с активным стримом:
   - отправляет итог (`sendRichMessage`, если `format=rich`, иначе `sendMessage`);
   - помечает стрим закрытым (черновик исчезает сам после отправки сообщения ботом);
   - если `reply` не был вызван, а пришёл `Stop`, черновик закрывается. Финального сообщения не отправляется, но если в черновике был текст, по настройке `STREAM_COMMIT_ON_STOP` его можно зафиксировать как сообщение.
6. **Кнопка «Стоп» с прерыванием хода.**
   - **Где кнопка:** в личке — нативная кнопка черновика (`can_stop=true`, Bot API 10.3, апдейт `stopped_message_generation`); в супергруппе — inline-кнопка «⏹ Стоп» (`style: danger`) под живым сообщением прогресса.
   - **Кто может нажать:** любой пользователь из allowlist, как у кнопок разрешений.
   - **Как прерывается ход.** Протокол канала прерывание не поддерживает. Поэтому:
     1. хук `SessionStart` передаёт демону `TMUX_PANE` из окружения сессии (хук наследует окружение Claude Code);
     2. по нажатию демон выполняет `tmux send-keys -t <pane> Escape` (через `execFile`, без shell). `Escape` прерывает текущий ход Claude Code;
     3. в ту же сессию отправляется событие `meta.event=stop_requested`, чтобы модель на следующем ходе знала, что её остановили;
     4. сообщение прогресса меняется на «⏹ Остановлено пользователем».
   - **Если сессия не в tmux** (`TMUX_PANE` пуст): кнопка всё равно показывается, но выполняет только п. 3. Пользователь получает всплывашку «Прерывание недоступно: сессия запущена не в tmux».
   - Настройка `STOP_MODE=interrupt|notify|off` (по умолчанию `interrupt`).
   - При реализации нужно проверить, что одиночный `Escape` прерывает ход и в состоянии ожидания разрешения не отклоняет запрос молча. Если это не так, ESC отправляется только когда сессия в статусе «работает».
7. **Группы и топики супергруппы (основной режим).** Draft-методы работают только в личке. В группах вместо черновика используются `sendChatAction(typing)` (с `message_thread_id`, обновляется каждые 4 с) и одно служебное сообщение «⏳ Работаю… (12 с)» с кнопкой «⏹ Стоп». Оно обновляется через `editMessageText` не чаще 1 раза в 3 с (лимиты Telegram на редактирование в группах строже, чем в личке). Итоговый `reply` удаляет его (по умолчанию) или заменяет на ответ (`PROGRESS_FINAL=delete|replace|keep`).
8. **Уровни подробности** — команда `/verbose 0|1|2` в чате:
   - 0: только «Thinking…» и итог;
   - 1 (по умолчанию): + строки действий из `PreToolUse`;
   - 2: + текст модели из `MessageDisplay`.
9. **Безопасность.** Строки прогресса не содержат значений, похожих на секреты: маскируются токены, ключи и пароли (по шаблонам) и содержимое `.env`. `tool_input` выводится кратко: имя файла, первые 80 символов команды.
10. **Хуки** поставляются плагином в `hooks/hooks.json`, тип `command`: маленький скрипт на Bun, который делает POST в демон с таймаутом ≤ 300 мс и **никогда не роняет и не задерживает** Claude Code. При недоступности демона он молча завершается с кодом 0.

### 2.4. Новые/изменённые инструменты

- `reply`: новый параметр `format: "text" | "markdownv2" | "rich"`. При `rich` текст передаётся как `InputRichMessage.markdown`.
- `stream_update` (опционально, для явного управления): `chat_id`, `text`, `thinking?`. Нужен для случаев, когда модель хочет показать промежуточный текст сама. По умолчанию модели не рекомендуется (тратит лимиты).

### 2.5. Критерии приёмки

- В личке после входящего сообщения в течение 1 с появляется «Thinking…».
- При `/verbose 1` каждый вызов инструмента отражается в черновике не позже чем через 1,5 с.
- Черновик не исчезает при ходе длиннее 30 с.
- После `reply` черновик исчезает, остаётся ровно одно итоговое сообщение.
- В топике супергруппы во время хода есть одно обновляемое сообщение прогресса с кнопкой «⏹ Стоп». После `reply` оно удаляется.
- Нажатие «⏹ Стоп» во время выполнения `Bash` с `sleep 60` в сессии под tmux прерывает ход не позже чем через 2 с.
- Ход, начатый в терминале, в Telegram ничего не стримит.
- Сбой демона или Bot API не ломает и не замедляет сессию Claude Code (проверяется остановкой демона во время хода).

## 3. Фича 2. Кнопки с вариантами ответа

### 3.1. Цель

Когда Claude предлагает пользователю выбор («вариант 1 или 2?», «ставим?», «да/нет»), в Telegram появляются кнопки. Ответить можно нажатием, не набирая текст.

### 3.2. Требования

1. Новый инструмент `ask_user`:
   - `chat_id`, `text` — вопрос;
   - `options`: массив 2–10 вариантов `{ label: string (≤ 40 символов), value?: string, style?: "primary"|"success"|"danger" }`;
   - `multi?: boolean` — множественный выбор с кнопкой «Готово»;
   - `allow_text?: boolean` (по умолчанию true) — разрешён свободный ответ текстом;
   - `timeout_min?: number` — после таймаута кнопки отключаются.
   
   Возвращает `question_id`.
2. Параметр `buttons` у `reply` — та же структура `options` для короткой формы без отдельного вопроса.
3. **`callback_data`** = `q:<question_id>:<index>` (≤ 64 байт). Полный текст вариантов хранится в SQLite, а не в кнопке.
4. **Нажатие:**
   - проверка отправителя по allowlist (как у кнопок разрешений);
   - `answerCallbackQuery` всегда;
   - в сессию уходит событие `notifications/claude/channel` с `content` = текст выбранного варианта и `meta`: `event=answer`, `question_id`, `option_index`, `option_value`;
   - сообщение редактируется: выбранный вариант отмечается ✅. Остальные кнопки становятся `disabled` (10.3) либо удаляются, если `disabled` недоступен. Повторное нажатие игнорируется.
5. Свободный текстовый ответ пользователя на сообщение с вопросом (reply-to) доставляется с `meta.question_id`, вопрос закрывается.
6. Если сессия была перезапущена, нажатие на старый вопрос всё равно доставляется. Вопрос хранится в SQLite, `meta.stale=true`, если вопрос создан в другой сессии.
7. **Инструкции канала:** «Если предлагаешь пользователю выбрать из нескольких вариантов или подтвердить действие — используй `ask_user`, а не перечисление в тексте».
8. Раскладка: до 3 кнопок в ряд при `label` ≤ 12 символов, иначе по одной в ряд.

### 3.3. Критерии приёмки

- Ответ на вопрос из 3 вариантов нажатием доходит до Claude как обычное сообщение с правильным `option_index`.
- Повторное нажатие и нажатие человеком не из allowlist не доставляются.
- Кнопки разрешений (`perm:*`) работают как раньше.

## 4. Фича 3. Исходящие голосовые сообщения

### 4.1. Цель

Claude может отвечать голосом: по просьбе, зеркально на голосовое пользователя или всегда.

### 4.2. Варианты синтеза речи (TTS)

| Вариант | Где | Качество русского | Цена | Задержка | Комментарий |
|---|---|---|---|---|---|
| **Silero TTS** (v4/v5, `ru`) | Локально, CPU (PyTorch) | Очень хорошее, натуральные русские голоса (`aidar`, `baya`, `kseniya`, `xenia`, `eugene`) | Бесплатно. Модели распространяются под некоммерческой лицензией: для личного бота подходит, перед коммерческим использованием проверить | ~1–2 с на абзац на CPU | **Выбран по умолчанию.** Требует Python + torch (~1–2 ГБ). |
| **Piper** (`ru_RU-*` голоса) | Локально, CPU | Хорошее, слегка «робот» | Бесплатно (MIT) | ~0,2–1 с на фразу | Один бинарник + модель ~60 МБ. **Фолбэк**, если Silero недоступен. |
| **XTTS-v2 / F5-TTS** | Локально, лучше GPU | Отличное, клонирование голоса | Бесплатно | На CPU медленно (секунды–десятки секунд) | Для «своего голоса». На текущем сервере без GPU только для коротких фраз. |
| **OpenAI TTS** (`gpt-4o-mini-tts` и др.) | Облако | Хорошее | Платно за символы | ~1 с | Текст уходит в OpenAI. |
| **ElevenLabs** | Облако | Отличное, клонирование | Платно, есть бесплатный лимит | ~1 с | Текст уходит в ElevenLabs. |
| **Yandex SpeechKit** | Облако | Отличное для русского | Платно | ~1 с | Текст уходит в Яндекс. |

Интерфейс `TtsProvider` с реализациями `silero` (по умолчанию), `piper` (фолбэк), `openai`, `elevenlabs`, `yandex`, `http` (произвольный OpenAI-совместимый `/v1/audio/speech`). Выбор через `.env`: `TTS_PROVIDER`, `TTS_VOICE`, `TTS_URL`, `TTS_API_KEY`, `TTS_FALLBACK`.

**Silero как локальный сервис.** Плагин написан на Bun, а Silero — Python/PyTorch, поэтому Silero запускается отдельным процессом-сервисом:

- `tts/silero_server.py` в репозитории: маленький HTTP-сервер на `127.0.0.1:<TTS_PORT>` с эндпоинтом, совместимым с OpenAI `/v1/audio/speech` (`input`, `voice`, `response_format`). Модель загружается один раз при старте и держится в памяти;
- отдельный venv в `STATE_DIR/tts/venv` (torch CPU-сборка), установка — `bewitched tts install` (скачивает модель `ru`, проверяет синтез тестовой фразы);
- демон запускает сервис по требованию при первом голосовом ответе и следит за ним (перезапуск при падении, остановка после `TTS_IDLE_MIN` простоя, по умолчанию 30 мин — модель занимает память);
- параметры: `TTS_VOICE` (по умолчанию `xenia`), `TTS_SAMPLE_RATE` (48000), `TTS_PUT_ACCENT`/`TTS_PUT_YO` (расстановка ударений и «ё», если поддерживается выбранной версией модели);
- длинный текст режется по предложениям (лимит модели на длину входа), куски склеиваются в один файл перед конвертацией в OGG/Opus;
- инструкция в `docs/tts-local.md`.

### 4.3. Требования

1. Инструмент `reply_voice`: `chat_id`, `text`, `reply_to?`, `caption?`. Также параметр `voice: true` у `reply`: голос + текст в подписи или отдельным сообщением (настройка `VOICE_WITH_TEXT=caption|message|none`).
2. Конвертация в OGG/Opus 48 кГц моно через `ffmpeg` с **массивом аргументов, без shell**. Отправка через `sendVoice` с `duration`.
3. **Подготовка текста:** вырезать markdown, ссылки и блоки кода (заменить на «код в сообщении»). Ограничение длины `VOICE_MAX_CHARS` (по умолчанию 1500), сверх лимита — текстом.
4. **Режимы** (`/voice off|mirror|always`, по умолчанию `mirror`): `mirror` — отвечать голосом, если входящее было голосовым.
5. Кэш по хэшу (текст+голос) в `STATE_DIR/tts-cache`, ротация по размеру.
6. Ошибка TTS не теряет ответ: отправляется текст и предупреждение в лог.
7. Облачные провайдеры включаются только явной настройкой ключа. В README описано, что текст уходит третьей стороне.

### 4.4. Критерии приёмки

- `reply_voice` в личке и в топике супергруппы приходит как голосовое с правильной длительностью и воспроизводится на Android/iOS/Desktop.
- Silero синтезирует абзац ~500 символов на текущем сервере быстрее чем за 5 с (после прогрева модели).
- При остановленном/сломанном Silero ответ приходит голосом Piper (если настроен фолбэк), иначе текстом.
- Локальные провайдеры работают без интернета (кроме Bot API).
- В режиме `mirror` на голосовое пользователя приходит голосовой ответ, на текстовое — текст.

## 5. Фича 4. Топики: топик на сессию/проект и главный топик управления

### 5.1. Цель

Каждый проект Claude Code получает свой топик в **отдельной форум-супергруппе**. Переписка разных задач не смешивается. Главным топиком управления служит «General» супергруппы (или выделенный топик «🎛 Пульт», настройка `CONTROL_TOPIC=general|pult`): из него видно все топики и сессии и можно ими управлять. Личка с ботом остаётся для служебного: подключение группы, запросы разрешений (по настройке), уведомления.

### 5.2. Площадка для топиков и подключение супергруппы

**Режимы** (`TOPICS_LOCATION`):
- `group` (по умолчанию) — топики в подключённой форум-супергруппе;
- `private` — топики в личке с ботом (нужен режим топиков в @BotFather, проверка `getMe().has_topics_enabled`);
- `off` — без топиков, как в официальном плагине.

**Подключение супергруппы из лички с ботом:**
1. Пользователь пишет боту в личку `/connect_group` (только владелец из allowlist). Бот отвечает пошаговой инструкцией и кнопкой «➕ Добавить в группу» — ссылка `t.me/<bot>?startgroup=<code>&admin=manage_topics+delete_messages+pin_messages`. Ссылка открывает выбор группы и сразу предлагает выдать боту права администратора.
2. Пользователь выбирает группу (или создаёт новую). Требования к группе проверяются автоматически:
   - супергруппа с включёнными темами (`is_forum`);
   - бот — администратор с правами `can_manage_topics` (обязательно), `can_pin_messages` (для закреплённой сводки), `can_delete_messages` (для удаления сообщений прогресса);
   - бот получает все сообщения группы: бот-администратор их видит независимо от privacy mode, это проверяется по факту прихода апдейтов.
3. Бот получает апдейт `my_chat_member` (добавлен в группу) и/или `/start <code>` в группе. Он сверяет код (одноразовый, живёт 15 мин) и отправителя (тот же владелец). Затем присылает в **личку** карточку «Подключить группу „<название>“?» с кнопками «✅ Подключить» / «❌ Отмена».
4. После подтверждения:
   - группа записывается в `access.json` → `groups[<id>]` с `requireMention: false` и `allowPaired: true` (писать в сессии и управлять ими могут все пользователи из allowlist бота; другие участники группы игнорируются);
   - в `topics.chat_id` сохраняется id группы, `TOPICS_LOCATION=group`;
   - в «General» группы публикуется и закрепляется сводка (§5.3.5);
   - для уже работающих сессий создаются топики.
5. Если чего-то не хватает (нет тем, нет прав), бот пишет в личку, что именно исправить, и предлагает кнопку «🔄 Проверить снова».
6. Команды в личке: `/group` — какая группа подключена, её статус и права бота; `/disconnect_group` — отвязать (топики и история остаются, сессии возвращаются в личку).
7. Если группу удалили или бота исключили (`my_chat_member` → `left`/`kicked`), бот уведомляет в личку и переключается на `TOPICS_LOCATION=private`/`off`.

**Ограничения режима `group`**, которые пользователь видит в README и в `/group`:
- нативный стриминг черновиками в группах недоступен, используется живое сообщение прогресса (§2.3.7);
- любой участник группы видит переписку с Claude. Группу следует держать приватной, без лишних участников.

### 5.3. Требования

1. **Реестр топиков** в SQLite (Bot API не даёт списка): `thread_id`, `chat_id`, `name`, `kind` (`session`/`project`/`manual`), `project_path`, `git_branch`, `session_id`, `status` (`active`/`idle`/`archived`), `created_at`, `last_activity_at`. Реестр пополняется и из сервисных сообщений `forum_topic_created` / `forum_topic_edited`, если пользователь создал топик вручную.
2. **Стратегия привязки** (`TOPIC_MODE`):
   - `off` — без топиков;
   - `project` (по умолчанию) — один топик на каталог проекта (`cwd`, имя — basename, при git — `repo · branch`). Новые сессии в том же каталоге переиспользуют топик;
   - `session` — новый топик на каждую сессию (имя: `проект · HH:MM`).
3. **Автосоздание:** при регистрации сессии в демоне (`SessionStart`) топик создаётся, если его ещё нет. В топик отправляется приветственная карточка: проект, ветка, модель, время.
4. **Маршрутизация:**
   - входящее в топике → сессия, привязанная к топику;
   - если привязанной активной сессии нет → сообщение получает главная сессия (§5.3b) и отвечает в этот же топик. Копия с пометкой «уже обработано» сохраняется для сессии проекта (§6.3);
   - если нет и главной сессии → ответ в топике «Сессия не запущена». Сообщение сохраняется и доставляется при следующем подключении сессии (§6.3);
   - исходящие инструменты по умолчанию пишут в топик своей сессии, `message_thread_id` подставляется автоматически;
   - запросы разрешений (`permission_request`) идут в топик сессии, которая их запросила, **только если** у группы `allowFrom` содержит ровно владельца (никто другой не может нажать кнопку — кнопки всё равно проверяют отправителя). Иначе — в личку, как в официальном плагине. Настройка `PERMISSIONS_TO=topic|dm|both` (по умолчанию `topic`).
5. **Главный топик / пульт.** Команды (работают только там и в личке без топика):
   - `/sessions` — список активных сессий: проект, топик, статус, время последнего действия, кнопки «Открыть топик», «Переименовать», «Архив», «Удалить»;
   - `/topics` — карточки активных сессий (как в `/sessions`: тип, статус, `#id`, pid, папка, ветка, топик, сессия/окно/панель tmux и команда `tmux attach`, доступность «Стоп», Remote Control, режим разрешений, модель и размер контекста (из транскрипта), текущий ход и последнее действие, `claude --resume <id>`, время работы и активности), затем топики без сессии с числом сообщений в очереди и архивные топики; кнопки управления топиками;
   - `/send <топик> <текст>` — отправить сообщение в сессию другого топика, не переходя туда;
   - `/broadcast <текст>` — во все активные сессии (с подтверждением кнопкой);
   - `/rename`, `/archive`, `/delete` (с подтверждением; `deleteForumTopic` удаляет и сообщения).
   
   Сводка-дашборд: одно закреплённое сообщение, которое демон обновляет через `editMessageText` не чаще раза в 10 с: сессии, их статус (работает / ждёт ответа / ждёт разрешения / простаивает).
6. **Архив.** «Закрыть» топик в личке API не умеет. Поэтому архив = статус в реестре + переименование с префиксом `🗄` + отвязка сессии.
7. Инструменты для модели: `create_topic(name)`, `rename_topic(thread_id, name)`, `list_topics()`, `delete_topic(thread_id)` (только с подтверждением пользователя кнопкой).

### 5.3a. Проекты из топиков (добавлено по ходу реализации)

- Владелец создаёт топик вручную → бот создаёт папку `PROJECTS_DIR/<имя топика>` (имя очищается: буквы любого алфавита, цифры, `.`, `-`, `_`), привязывает к ней топик и запускает в новом окне tmux (`TMUX_SESSION`) команду `CLAUDE_LAUNCH_CMD` в этой папке.
- Бот пишет в топик номер окна и как подтвердить экран `--dangerously-load-development-channels`. Подтверждение нажимает пользователь — бот его не автоматизирует.
- Сессия, запущенная в папке, подключается к уже привязанному топику и не создаёт новый.
- `TOPIC_PROJECTS=auto|ask|off` (по умолчанию `auto`; `ask` — подтверждение кнопкой). Топики других участников группы игнорируются.
- Команда `/new_session <имя|путь>` в пульте — то же без ручного создания топика.

### 5.3b. Главная сессия (v1.0.1)

- Личка с ботом отделена от топиков проектов. Лички всех пользователей из allowlist и обычный текст в General получает **главная сессия**. Проектные сессии личку не получают.
- Главная — активная сессия, запущенная в папке `MAIN_DIR` (по умолчанию домашняя папка пользователя, под которым работает демон). Команда `/main <id>` в личке делает главной папку другой сессии, `/main reset` возвращает `MAIN_DIR`, `/main` без аргументов показывает текущую. Кнопка «👑 Главная» в `/sessions` — то же, что `/main <id>`. `/use` остаётся синонимом `/main`.
- У главной сессии нет своего топика: при подключении топик не создаётся, приветственной карточки нет.
- Топик проекта без запущенной сессии обслуживает главная: сообщение приходит к ней с `thread_id`, и она отвечает в этот топик. То же для `/send` в топик без сессии.
- Неизвестные команды в General в сессию не передаются.
- Если главная не запущена: сообщения из лички и General сохраняются в очередь главной, бот отвечает «💤 Главная сессия не запущена». При подключении главной они приходят в `session_resume`.

### 5.4. Критерии приёмки

- Две сессии в разных каталогах автоматически получают два топика. Сообщения в каждом доходят только до своей сессии.
- Перезапуск сессии в том же каталоге (`TOPIC_MODE=project`) продолжает тот же топик.
- `/sessions` в пульте показывает обе сессии. `/send` доставляет сообщение в нужную.
- Подключение новой супергруппы через `/connect_group` проходит от команды до закреплённой сводки без ручного ввода id. При нехватке прав бот называет конкретное недостающее право.
- Сообщение в топике от участника группы не из `allowFrom` не доходит до сессии.
- В режиме `private` при выключенных топиках в BotFather плагин работает как раньше и пишет понятное предупреждение.

## 6. Фича 5. Сообщения в топик без инициирующего сообщения

### 6.1. Цель

Сообщить пользователю о завершении долгой задачи, сборки, ошибки или напоминания, даже если он ничего не писал.

### 6.2. Требования

1. Инструмент `notify`: `text`, `topic?` (thread_id или имя; по умолчанию топик текущей сессии), `silent?` (`disable_notification`), `files?`, `buttons?`. Не требует `chat_id`: адресат — владелец бота (первый из `allowFrom`, либо `NOTIFY_CHAT_ID`).
2. **Автоуведомление о завершении хода** (хук `Stop`), настройка `/notify_done off|long|always`:
   - `long` (по умолчанию) — если ход длился дольше `NOTIFY_LONG_SEC` (по умолчанию 60 с) **и** не закончился вызовом `reply`;
   - текст: «✅ Готово за 3 мин 12 с» + первые 300 символов `last_assistant_message`;
   - для `StopFailure` — «❌ Ход завершился с ошибкой».
3. **Внешний вход:** CLI `bewitched notify --topic <имя> "текст"` и HTTP `POST 127.0.0.1:<port>/notify` с bearer-токеном из `STATE_DIR/.env`. Скрипты, cron и CI могут писать в топик без участия Claude.
4. **Внешние события в сессию.** `POST /event` с `topic` и `text` превращается в `notifications/claude/channel` для сессии этого топика (`meta.event=external`, `meta.source_name`). Claude начинает работать без сообщения пользователя. Сценарии: вебхук CI, алерт мониторинга. По умолчанию выключено, включается `EVENTS_ENABLED=true`. Каждый внешний источник отмечается в `meta`, чтобы модель не считала его словами пользователя.
5. Rate limit на `notify`/`/event` (по умолчанию 20 в минуту на топик), защита от циклов. Событие, вызванное уведомлением бота, не порождает новое событие.

### 6.3. Отложенная доставка

Входящие в топик без активной сессии хранятся в SQLite. При подключении сессии к топику они доставляются одним событием: «Пока сессия была offline, пришло N сообщений» + сами сообщения. Срок хранения `PENDING_TTL_H` (по умолчанию 72 ч).

Сообщения, на которые уже ответила главная сессия (§5.3b), тоже доставляются сессии проекта при подключении, но отдельным блоком «для контекста, повторно не отвечай». В `pending_count` они не входят. Сообщения в личку и General, пришедшие без главной сессии, хранятся в отдельной очереди и доставляются главной.

### 6.4. Критерии приёмки

- `notify` из сессии без входящего сообщения приходит в правильный топик с пушем.
- Ход длиннее 60 с без `reply` порождает уведомление «Готово». Короткий ход — нет.
- `curl -H "Authorization: Bearer …" -d … 127.0.0.1:<port>/notify` доставляет сообщение. Без токена — 401.

## 7. Фича 6. Общий демон опроса

### 7.1. Цель

Несколько сессий Claude Code одновременно работают с одним ботом без 409 Conflict. Дочерние процессы (`claude -p`, субагенты) не роняют основной канал.

### 7.2. Требования

1. **Единственность.** Демон берёт эксклюзивную блокировку `STATE_DIR/daemon.lock` (flock). Второй экземпляр не стартует, а подключается к существующему как клиент.
2. **Запуск.** Первый MCP-сервер, не нашедший живой демон, запускает его как отдельный процесс (detached, `setsid`), stdout/stderr — в `STATE_DIR/logs/daemon.log` с ротацией. Ручное управление: `bewitched daemon start|stop|restart|status|logs`. Для старта после перезагрузки сервера — строка `@reboot` в cron (`bewitched daemon install-cron`). systemd не используется: текущий сервер — контейнер без systemd.
3. **Остановка.** По умолчанию демон работает постоянно (`DAEMON_IDLE_EXIT_MIN=0`), чтобы `/notify`, отложенная доставка и пульт работали, даже когда ни одна сессия не запущена. Если задать `DAEMON_IDLE_EXIT_MIN>0`, демон завершается после этого времени без клиентов, предварительно сохранив отложенные входящие. Пока нет ни одной сессии, на сообщения в топиках демон отвечает «Сессия не запущена» (§5.3.4).
4. **Протокол клиента** (unix-сокет, JSON-lines, версия протокола в `hello`):
   - `hello { session_id, cwd, git_branch, pid, protocol }` → `welcome { topic, chat_id }`;
   - `inbound { … }` (демон → клиент), `tool_call { name, args }` / `tool_result` (клиент → демон);
   - `permission_request` / `permission_verdict`;
   - `ping` / `pong` каждые 15 с. Клиент без pong 45 с считается мёртвым.
5. **Отправка** идёт через демон: общая очередь с учётом лимитов Telegram, повтор при `429 retry_after`, приоритет у ответов на кнопки и разрешений.
6. **Сессии без канала.** MCP-сервер, запущенный в сессии, где канал не зарегистрирован (`claude -p`, SDK), не должен получать входящие. Он регистрируется как `passive`: может вызывать исходящие инструменты (если разрешено `PASSIVE_TOOLS=true`), но не забирает сообщения и не создаёт топики. Признак — отсутствие `notifications/claude/channel` capability у клиента, либо явная переменная окружения от хука `SessionStart`.
7. **Падение демона.** Клиенты переподключаются с экспоненциальной задержкой (до 15 с) и при необходимости перезапускают демон. Входящие за время простоя Telegram держит до 24 ч, после старта они забираются через `getUpdates` с сохранённым `offset`.
8. **Совместимость:** при обнаружении работающего официального плагина (`bot.pid` в старом каталоге с живым `server.ts`) — предупреждение и отказ от опроса, а не «убийство» чужого процесса.
9. **Наблюдаемость:** `/status` в пульте и `bewitched status` в терминале показывают PID демона, аптайм, подключённые сессии, длину очереди, последние ошибки Bot API.

### 7.3. Критерии приёмки

- Две сессии + `claude -p "..."` запущены одновременно: 409 не возникает, обе сессии получают свои сообщения.
- `kill -9` демона во время работы: в течение 20 с он перезапускается, сообщения, отправленные в это время в Telegram, доставляются.
- Закрытие всех сессий: демон продолжает работать, `/notify` и пульт отвечают. При `DAEMON_IDLE_EXIT_MIN>0` демон завершается через заданное время.

## 8. Фича 7. История и память, контекст ответов, цитаты, пересылки

### 8.1. Цель

Claude знает, о чём шла речь раньше, даже после перезапуска. Он видит, на какое сообщение отвечает пользователь, какую часть цитирует и откуда переслано сообщение.

### 8.2. Хранилище

- SQLite (`bun:sqlite`), `STATE_DIR/history.db`, WAL, права 0600.
- Таблица `messages`: `chat_id`, `thread_id`, `message_id`, `direction` (in/out), `from_id`, `from_name`, `date`, `text`, `kind` (text/photo/voice/…), `file_id`, `local_path`, `transcript` (для голосовых), `reply_to_message_id`, `quote_text`, `forward_origin_json`, `session_id`.
- FTS5-индекс по `text` + `transcript` для поиска.
- Ротация: `HISTORY_MAX_DAYS` (по умолчанию 90) и/или `HISTORY_MAX_MB`. Команда `/forget` в чате удаляет историю топика (с подтверждением).

### 8.3. Обогащение входящих

К событию `notifications/claude/channel` добавляются атрибуты `meta` (только безопасные ключи, значения очищаются функцией `safeName`-подобной санитизации и обрезаются):

| Ключ meta | Источник | Содержимое |
|---|---|---|
| `reply_to_message_id` | `reply_to_message.message_id` | ID |
| `reply_to_from` | `reply_to_message.from` | `bot` или имя |
| `reply_to_text` | `reply_to_message.text/caption`, иначе из истории | до 300 символов |
| `quote_text` | `quote.text` (TextQuote) | до 300 символов |
| `forward_from` | `forward_origin` | тип и имя (`user:Иван`, `channel:Новости`, `hidden_user:…`) |
| `forward_date` | `forward_origin.date` | ISO |
| `external_reply_from` | `external_reply.origin` | для ответов на сообщения из других чатов |
| `thread_id`, `topic_name` | топики | |

Если исходного текста в апдейте нет (старое сообщение), он берётся из истории по `message_id`. **Пересылки пачкой** (несколько forward за ≤ 3 с от одного отправителя) собираются в одно событие со списком.

### 8.4. Инструменты

- `get_history(chat_id?, topic?, limit=30, before_message_id?)` — последние сообщения в компактном формате.
- `search_messages(query, topic?, limit=20)` — поиск FTS.
- `get_message(message_id)` — одно сообщение целиком, включая вложения и расшифровку.

### 8.5. Память между перезапусками

1. **Сводка топика:** файл `STATE_DIR/memory/<thread_id>.md`. Обновляется инструментом `save_memory(text)` по команде пользователя `/remember` или при `/new` (сброс контекста): модель пишет краткую сводку.
2. **При подключении сессии к топику** (§7.2 `hello`) демон отправляет первое событие с `meta.event=session_resume`: сводка топика + последние `RESUME_LAST_N` (по умолчанию 10) сообщений. Так новая сессия сразу в контексте.
3. Инструкции канала: «История доступна через `get_history` и `search_messages` — используй их, если пользователь ссылается на прошлое».

### 8.6. Критерии приёмки

- Ответ пользователя reply-to на сообщение бота доходит с `reply_to_text` (текст исходного сообщения бота).
- Цитата части сообщения доходит в `quote_text`.
- Пересланное из канала сообщение доходит с `forward_from=channel:<имя>`.
- После перезапуска сессии модель может ответить на вопрос «что я тебе писал час назад?» через `get_history`.

## 9. Фича 8. Расшифровка входящих голосовых (STT)

### 9.1. Цель

Голосовые и кружки пользователя автоматически превращаются в текст до того, как попадут к Claude. Сервис расшифровки может работать локально.

### 9.2. Варианты

| Вариант | Где | Комментарий |
|---|---|---|
| **whisper.cpp server** (`whisper-server`, модели `small`/`medium`/`large-v3-turbo`) | Локально, CPU | Без Python, OpenAI-совместимый эндпоинт. На текущем сервере (28 ядер, 31 ГБ RAM) `small`/`medium` работают быстрее реального времени. **Рекомендуется по умолчанию.** |
| **faster-whisper** (`speaches` / `faster-whisper-server`) | Локально, CPU/GPU | OpenAI-совместимый API, Docker. |
| **Vosk** | Локально, CPU | Очень лёгкий, качество ниже Whisper. |
| **OpenAI** (`gpt-4o-mini-transcribe`, `whisper-1`) | Облако | Аудио уходит в OpenAI. |
| **Groq** (whisper-large-v3) | Облако | Очень быстро, есть бесплатный лимит. |
| **Deepgram** | Облако | Быстро, платно. |
| **Yandex SpeechKit** | Облако | Хорош для русского. |

### 9.3. Требования

1. Интерфейс `SttProvider` (`transcribe(file, mime, lang?) → { text, language, duration, provider }`). Реализации: `openai-compatible` (покрывает whisper.cpp, faster-whisper, OpenAI, Groq — разница в `STT_URL`/ключе), `deepgram`, `yandex`, `vosk-ws`.
2. Настройки `.env`: `STT_PROVIDER`, `STT_URL`, `STT_API_KEY`, `STT_MODEL`, `STT_LANGUAGE` (по умолчанию авто), `STT_FALLBACK` (цепочка провайдеров через запятую), `STT_MAX_SEC` (по умолчанию 600).
3. Обрабатываются `voice`, `audio`, `video_note` (дорожка извлекается `ffmpeg`), опционально `video` (`STT_VIDEO=true`). Файл скачивается только **после** проверки доступа (как сейчас с фото).
4. В событие для Claude:
   - `content`: расшифровка (если есть подпись — `подпись\n\n🎤 расшифровка`);
   - `meta`: `attachment_kind`, `voice_transcribed=true`, `voice_duration`, `voice_language`, `stt_provider`, `attachment_file_id` (оригинал остаётся доступен через `download_attachment`).
5. Во время расшифровки ставится реакция ✍ (если включены ack-реакции), после — обычный ack.
6. Ошибка STT: событие доставляется как сейчас (`(voice message)` + `attachment_file_id`) с `meta.stt_error`.
7. Расшифровка сохраняется в истории (§8) и попадает в поиск.
8. Опция `/transcript on|off` — показывать ли пользователю в чате текст расшифровки ответом на его голосовое (удобно проверять качество).
9. В `docs/stt-local.md` — инструкция по установке whisper.cpp server как systemd-сервиса на этом сервере.

### 9.4. Критерии приёмки

- Голосовое 30 с на русском расшифровывается локальным провайдером быстрее чем за 10 с на текущем сервере и доходит до Claude текстом.
- При недоступном локальном сервисе срабатывает фолбэк, если он задан, иначе приходит исходное поведение с `stt_error`.
- Без настройки STT плагин ведёт себя как официальный (голосовое — вложение).

## 10. Общие требования

### 10.1. Безопасность

- Все правила доступа официального плагина сохраняются: pairing, allowlist, проверка отправителя у **всех** кнопок, запрет отправки файлов из `STATE_DIR`, санитизация имён в meta, предупреждение о prompt-injection в инструкциях.
- Внешние вызовы процессов — только `execFile`/`spawn` с массивом аргументов.
- HTTP-интерфейс демона: только `127.0.0.1`, bearer-токен, лимит размера тела 1 МБ.
- Облачные STT/TTS включаются только явной настройкой. Аудио и текст уходят третьей стороне — это описывается в README.
- Права файлов состояния: каталоги 0700, файлы 0600.
- Секреты не пишутся в логи. В строках прогресса стрима — маскирование (§2.3.9).

### 10.2. Конфигурация

- Все настройки — в `STATE_DIR/.env` и `access.json` (UX-настройки, как сейчас). Команды в чате (`/verbose`, `/voice`, `/notify_done`, `/transcript`) пишут в `access.json` → секция `prefs` на уровне чата/топика.
- Каждая фича выключаема. При всех выключенных фичах поведение совпадает с официальным v0.0.7.

### 10.3. Совместимость и обновления

- Ведётся `UPSTREAM.md`: от какого коммита официального плагина сделан форк, как подтягивать изменения (`git subtree pull` / ручной merge).
- Версионирование SemVer, начиная с `0.1.0`. Changelog в `CHANGELOG.md`.
- Минимальная версия Claude Code — та, где есть хук `MessageDisplay` и channels. Проверяется при старте через `claude --version` из хука `SessionStart`. При несоответствии — предупреждение и отключение стриминга.

### 10.4. Качество

- TypeScript strict, Biome (lint/format).
- Тесты `bun test`: unit для маршрутизации, chunk/обрезки, санитизации meta, парсинга callback, провайдеров (с моками HTTP). Интеграционные — с фейковым Bot API-сервером (локальный HTTP, `apiRoot` в grammY).
- CI на GitHub Actions: typecheck, lint, test на каждый PR в `develop`.
- Код разбит на модули: `daemon/`, `client/`, `telegram/` (обёртка Bot API 10.x), `stream/`, `topics/`, `history/`, `stt/`, `tts/`, `hooks/`.

## 13. Feature requests (последующие этапы)

### FR-1. Стриминг самого ответа («ответ из транскрипта»)

Сейчас стримится ход работы, а ответ приходит целиком через `reply` (решение 1). FR-1 добавляет стриминг текста ответа.

- Флаг `STREAM_ANSWER_FROM_TRANSCRIPT=true`, выключен по умолчанию.
- Инструкции канала просят модель писать ответ пользователю обычным текстом в транскрипт, а затем вызывать `reply` с `use_last_message: true` (без дублирования текста в аргументах).
- Демон отображает пачки `MessageDisplay` как текст ответа: в личке — черновиком (`sendRichMessageDraft`), в группе — правками живого сообщения. При `reply(use_last_message)` фиксирует итог из `Stop.last_assistant_message` или накопленных пачек.
- Минусы, которые нужно решить при проектировании: в транскрипте смешиваются ответ и рассуждения (нужен маркер начала ответа); правки в группе ограничены по частоте; модель может забыть вызвать `reply` (страховка — фиксация по `Stop`).
- Зависимости: этапы 3 и 4.

### FR-2. Клонирование своего голоса для TTS

XTTS-v2 / F5-TTS или ElevenLabs Voice Clone. Нужна GPU или облако. Рассматривается после этапа 7.

### FR-3. Топики в нескольких супергруппах

Например, рабочие и личные проекты в разных группах с правилом маршрутизации по пути проекта.

### FR-4. Работа нескольких пользователей с топиком

Решение 2026-10-28: все пользователи из allowlist бота имеют одинаковые полные права (писать, пульт, кнопки, разрешения, архив) — `allowPaired: true` у группы топиков. Остаётся продумать более тонкие роли для случаев, когда это понадобится. Нужно продумать совместную работу нескольких людей с одним топиком или сессией. Вопросы для проработки:

- **Роли:** владелец / участник / наблюдатель (только чтение). Кто может писать в сессию, нажимать «⏹ Стоп», отвечать на `ask_user`, одобрять разрешения.
- **Разрешения инструментов:** официальный плагин намеренно шлёт их только в личку владельцу («single-user mode»). Можно ли доверять одобрение другим участникам и как это ограничить (например, только безопасные инструменты или только владелец).
- **Атрибуция:** модель должна видеть, кто именно пишет (`user`, `user_id` уже есть в meta), и понимать, чьи указания главнее при конфликте.
- **Безопасность:** участник может попытаться дать модели команду, которую владелец бы не одобрил (prompt injection изнутри группы). Нужны правила в инструкциях канала и, возможно, ограничение инструментов для сообщений не от владельца.
- **Очередь и параллельные сообщения:** как сессия обрабатывает сообщения от нескольких людей во время одного хода.
- **Управление доступом:** добавление участников в топик из пульта (`/topic_access`), доступ на уровне группы или конкретного топика.
- **Приватность истории:** видят ли новые участники прошлую историю топика и `get_history`.
